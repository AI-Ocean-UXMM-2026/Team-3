# Database Architecture Specification — LannPya AI (လမ်းပြ)

This document outlines the authoritative database architecture, data models, entity relationships, and concurrency controls for the LannPya AI middleware platform.

---

## 1. System Topology & Tier Isolation

```text
+-----------------------------+
|   Frontend User Interface   |  (No DB credentials; uses capability tokens & session cookies)
+-----------------------------+
               |
               v HTTPS REST API
+-----------------------------+
|     FastAPI Middleware      |  (RBAC, Token Validation, Audit Logging)
+-----------------------------+
               |
               v SQLAlchemy 2.0 (psycopg 3)
+-----------------------------+
|  Supabase Hosted PostgreSQL |  (or SQLite fallback for offline local testing)
+-----------------------------+
```

### Core Security Invariants
* **Zero Client Credentials**: The browser client NEVER receives `DATABASE_URL` or service-role keys.
* **Dialect Agnostic ORM**: SQLAlchemy 2.0 with the `psycopg` driver manages all transactions.
* **Dual Backend Support**: The identical codebase runs seamlessly on local SQLite and hosted PostgreSQL.

## 2. Canonical Data Models & Schemas

The database schema comprises **14 tables** across 5 functional domains:

### A. Identity & Core Order Management
1. **`users`**: Platform actors (`Merchant`, `Dispatcher`, `Rider`, `Admin`).
   * Primary Key: `UUID`
   * Constraints: Validated email (`length BETWEEN 3 AND 254`), non-empty name, role enum constraint.
2. **`orders`**: Central parcel & delivery record.
   * Primary Key: `UUID`
   * Foreign Keys: `merchant_id -> users.id (RESTRICT)`
   * Geospatial: `latitude NUMERIC(10, 7)`, `longitude NUMERIC(10, 7)` bounded between -90/90 and -180/180.
   * Financial: `cod_amount NUMERIC(12, 0)` with integer-only constraint (`cod_amount = CAST(cod_amount AS BIGINT)`).
   * Concurrency: `version INTEGER` for optimistic concurrency control (`version_id_col`).
   * Provenance & AI: `confidence_level` (`GREEN`, `AMBER`, `RED`), `confidence_reasons JSONB`, `field_sources JSONB`, `parsing_metadata JSONB`.
   * Status Lifecycle: `DRAFT`, `NEEDS_REVIEW`, `AWAITING_CONFIRMATION`, `CONFIRMED`, `READY_FOR_DISPATCH`, `ASSIGNED`, `OUT_FOR_DELIVERY`, `DELIVERED`, `FAILED`, `CANCELLED`.
3. **`delivery_events`**: Immutable audit log of every lifecycle change and state transition.
   * Columns: `order_id`, `event_type`, `previous_status`, `new_status`, `metadata JSONB`, `created_at`.
   * Index: Composite chronological index `(order_id, created_at, id)`.

### B. Buyer Capability & Verification
4. **`confirmation_links`**: Ephemeral capability links sent to buyers.
   * Columns: `order_id`, `token_hash` (SHA-256), `phone_binding` (salted hash), `expires_at`, `failed_attempts` (0–3 lockout), `generation`, `nonce`.
5. **`buyer_sessions`**: Authenticated temporary buyer sessions.
   * Foreign Key: `link_id -> confirmation_links.id (RESTRICT)`.
6. **`location_references`**: Dispatcher-attested physical anchors.
   * Foreign Key: `order_id -> orders.id (Primary Key)`, `actor_id -> users.id`.
7. **`buyer_requests`**: Buyer-submitted location or delivery window corrections awaiting dispatcher approval.
   * Columns: `payload_hash`, `kind` (`LOCATION`, `RESPONSE`), `decision` (`APPLIED`, `REVIEW_REQUIRED`), `resolution` (`APPROVE`, `REJECT`), `reason_codes JSONB`.
   * Unique Index: Idempotent submission retry guard `(link_id, request_id)`.
8. **`buyer_rate_limits`**: Atomic fixed-window rate limiter keys.

### C. Rider Operational Co-Pilot
9. **`rider_profiles`**: Operational state of delivery riders.
   * Primary Key: `id -> users.id`
   * Columns: `operational_status` (`AVAILABLE`, `ON_BREAK`, `OFFLINE`), `queue_version INTEGER`, `version INTEGER`.
10. **`delivery_assignments`**: Active and historical order dispatches to riders.
    * Columns: `order_id`, `rider_id`, `dispatcher_id`, `status` (`ACTIVE`, `UNASSIGNED`, `COMPLETED`, `FAILED`, `CANCELLED`), `stop_sequence`, `cod_collected BOOLEAN`.
    * Partial Unique Index: `(order_id) WHERE status = 'ACTIVE'` ensures an order cannot be actively assigned to multiple riders simultaneously.
11. **`rider_action_receipts`**: Idempotent action deduplication store.
    * Unique Index: `(actor_id, request_id)` prevents double-submission of delivery confirmations or cash collections.

### D. Workflow & Routing Optimization
12. **`workflow_routes`**: Route plans and cash reconciliation state.
13. **`routing_plans`**: Multi-stop VRP route plans generated by OR-Tools solver.
    * Columns: `actor_id`, `version`, `state` (`PREVIEW`, `COMMITTED`), `data JSONB`.
14. **`routing_rate_limits`**: Rate limiting tokens for route optimization requests.

## 3. Concurrency & Data Integrity Strategy

### Optimistic Locking
`Order`, `RiderProfile`, and `RoutingPlan` use SQLAlchemy optimistic locking:
```python
__mapper_args__ = {"version_id_col": version}
```
If two dispatchers or automated processes attempt to modify the same order simultaneously, SQLAlchemy detects the version mismatch and raises `StaleDataError`. The application converts this into an HTTP 409 conflict, prompting the client to reload the latest state rather than silently overwriting changes.

### Foreign Key Protection
Every foreign key explicitly declares `ondelete="RESTRICT"`. No cascading deletes are permitted; historical audit logs, financial records, and orders cannot be inadvertently pruned.

### High-Precision Financial Data
COD amounts are stored using PostgreSQL `NUMERIC(12, 0)` rather than floating-point numbers, preventing currency rounding discrepancies. Myanmar Kyat (MMK) operates without fractional subunits; this constraint is verified at the database level:
```sql
CHECK (cod_amount IS NULL OR (cod_amount >= 0 AND cod_amount <= 1000000000 AND cod_amount = CAST(cod_amount AS BIGINT)))
```
